# 拼多多接口草稿提交验证

更新：2026-10-09。0.1.63正式版新建拼多多任务默认API，已有任务按原方式恢复。2026-10-08的试用及后台验证记录保留在下文。

## 当前实现

`electron/platforms/pdd-api-draft.ts`通过现有浏览器会话调用页面API客户端，复用登录及店铺核对、任务队列和保存意图记录。执行流程已包括类目搜索、编号分配、属性/规格映射、图片上传、商品与详情保存、属性及图片读回，以及按原编号查询草稿箱。商品表单的逐项DOM填写由接口请求替代，浏览器仍负责登录、身份核对和正常请求上下文。

正式版直接创建新任务即可使用API；开发环境运行`pnpm dev`。新任务固定保存`executionMode: pdd_api`，旧任务没有该字段时继续原DOM流程。不提供执行中切换方式或静默回退。

此次实际验证使用Windows虚拟机的Edge浏览器和已登录Mandla旗舰店。以已安装0.1.61的Electron/Node运行时运行当前编译源码，任务编码`API-CURRENT-20261008-321`，商品编号`1013813482840`，草稿编号`203079569925`。完成了编号创建、27张不同原图上传（对应30个图片位置）、四个SKU保存，以及标题编码、类目、四项属性、价格库存规格编码/图、十张主图、十六张详情图、参考价折扣、运费、发货和三项售后承诺读回。草稿箱接口按商品ID返回唯一编辑中记录。没有提交上架。

这一验证是**当前源码组件在真实Windows/Edge后台执行的证明**，不是新版安装包的GUI安装验收。此前商品编码、价格库存的修改/恢复实验仍保留在下文。

另用同一商品快照把第一个SKU库存明确设为0，测试编码`API-ZERO-20261008-321`，商品编号`1013824517052`、草稿编号`203082763945`。保存与全部字段核验通过；首次列表查询遇到索引延迟，随后用最新源码只读恢复确认唯一草稿，没有重建或重复保存。其余三个SKU库存仍为2000，原Excel文件未修改。

## 支持范围与恢复

- 当前针对新建普通商品草稿；类目属性支持独立单选，关联规格模板及其他控件类型明确停止。
- 支持当前类目允许的24小时/48小时发货；正品发票为“是”的发票类型设置尚未接入。
- 价格按分提交，完整规格矩阵按名称和值映射；库存针对新草稿基数0的`quantity_delta`，不开放修改在售商品库存。
- 图片逐张上传并保存本任务记录，已确认的同一原图复用；商品与富文本详情分别保存并核验地址、数量和顺序。
- 分配编号前记录创建意图；响应不明且未取得编号时停止，不再次创建。保存前持久化保存意图，已尝试保存的恢复分支只查询原编号，不重新保存或分配编号。
- 新保存草稿的列表索引可能延迟；最终确认阶段最多等待20秒，以间隔读取确认唯一记录。等待结束仍未确认时保留原编号，继续只读恢复。
- 不支持的模板、发货或承诺停止并提示，不自动切回DOM写入。
- 其他店铺、其他类目、大批量和长期稳定性仍待验证；Mac真实后台API执行及完整运营GUI验收尚未完成，本机试用包启动核验见下文。

## 结论与实测范围

本节保留最初的字段修改与恢复实验；当前整件商品的API源码验证见上文“当前试用实现”。

在Windows虚拟机的Edge浏览器中，复用已登录的Mandla旗舰店会话，通过拼多多页面自带的`window.__mms.fetch.post`，成功直接读取和更新一件专用测试草稿。修改和读回步骤没有操作表单控件。

移除临时观察脚本并重新加载编辑页后，再通过现有`BrowserBridge`使用的`evaluate`命令调用API，商品及详情读取仍通过。该方式不依赖观察脚本或复制出来的请求头。

测试资料为`321.xlsx`，文件SHA256为`92de661ecd1e3ce3d205573555af8c447ac1f0fa5df41012673c115c089dcb64`。测试草稿编码为`API-PROBE-20261008-321`，包含四个SKU、四张规格图、十张主图、十六张详情图。初始编号创建及图片上传通过原0.1.61流程完成，后续接口实验沿用同一件草稿。

| 操作 | 结果 |
| --- | --- |
| 普通`fetch`调用商品读取接口 | HTTP 200，但业务返回2000000，未取得商品数据 |
| 普通`fetch`复用观察到的请求头 | 同样被拒绝，不能把捕获的校验值写死使用 |
| 页面原有API客户端读取草稿 | 正确取得商品编号、商家编码、四个SKU及图片记录 |
| 接口修改商家编码并读回 | 临时追加`-API`后读回一致，再恢复原编码并确认 |
| 接口修改SKU 1的拼单价、单买价、库存并读回 | 119.99→120.00元、120.99→121.00元、2000→2001；读回一致，其他三个SKU保持一致 |
| 恢复SKU原数据并读回 | 四个SKU的价格、库存、编码、规格选项及规格图绑定恢复一致，主图10张、详情图16张 |

所有写操作只作用于专用测试草稿。测试结束保留该草稿供核对，没有点击提交上架。

## 已确认的接口链路

下表是本次真实商家页面使用的内部接口，不是已申请授权的开放平台接口。后续适配需要检查当前页面客户端是否仍提供这些能力。

| 用途 | 方法与路径 | 实测情况 |
| --- | --- | --- |
| 保存商品字段、SKU、图片记录、发货及服务设置 | POST `/glide/mms/goodsCommit/action/edit` | 正常保存草稿请求已捕获；API直接修改字段和SKU通过 |
| 保存富文本详情 | POST `/glide/forward/gorse/mms/goods/decoration/commit/save` | 正常页面保存请求及成功响应已捕获；本次未独立修改详情 |
| 读回原草稿商品 | POST `/glide/v2/mms/query/commit/detail` | API直接调用通过 |
| 读回富文本详情 | POST `/glide/forward/gorse/mms/goods/decoration/commit/query/V2` | API直接调用通过，返回十六个图片楼层及十六张详情图 |
| 查询当前类目属性模板 | GET `/draco-ms/mms/template/mall` | 正常页面请求已捕获；尚未实现通用模板映射 |

商品保存与详情装修分为两条链路，需要分别确认结果。此次原DOM保存读回曾报告详情图0/16，但接口返回的商品图片记录和富文本详情均有16张，说明不能只靠DOM数量判断详情丢失。

## 请求方式

保留浏览器登录、人工验证码处理和店铺身份核对，在正确的商家页面执行页面已有API客户端，由它生成当前请求上下文。不要保存Cookie、复制`anti-content`值或自行重写校验算法。

只读调用形式如下。`goodsId`和`commitId`须来自当前任务，并与页面URL及响应编号核对，不能引用另一个任务的编号：

```js
const draft = await window.__mms.fetch.post(
  '/glide/v2/mms/query/commit/detail',
  { goods_id: goodsId, goods_commit_id: commitId },
);
```

此次页面客户端返回的是解包后的商品对象，包含`draft.goods_id`、`draft.id`、`draft.sku`，不是原始网络响应的`{ success, result }`外层结构。业务失败需要按客户端异常处理，不能只检查HTTP状态。

## 字段映射要点

| 本机字段 | 本次真实保存字段 | 需要保留的语义 |
| --- | --- | --- |
| 商品标题、编码 | `goods_name`、`out_goods_sn` | 保存后按原编号读回 |
| 类目 | `cat_id`、`cat_ids`、`cats` | 从当前类目接口解析路径与编号，不能只传末级文字 |
| 类目属性 | `goods_properties`、`goods_property_group` | 根据当前类目模板映射属性和值ID |
| 草稿编号 | `goods_commit_id` | 商品保存请求使用字符串；详情保存接口使用数值，不混用请求模型 |
| SKU选项 | `skus[].spec` | 包含规格类型及选项ID；按名称和值核对组合，不能按行号猜对应关系 |
| 拼单价 | `multi_price`、`multi_price_in_yuan` | 金额字段单位为分；本次119.99元对应11999，同时保持元文本一致 |
| 单买价 | `price`、`price_in_yuan` | 与拼单价相同单位规则 |
| 库存 | `quantity_delta` | 本次新建草稿读回`quantity=0`、`quantity_delta=2000`，不能把前者当作目标库存0；已有商品库存修改语义另行验证 |
| 规格编码、图 | `out_sku_sn`、`thumb_url` | 图片先完成上传，再将返回地址绑定到正确SKU |
| 主图及详情图记录 | `gallery`；读取对象为`galleries` | 本次type 1为主图、type 2为详情图；同时核对富文本详情链路 |
| 富文本详情 | `decoration_floor_list` | 独立保存，保留图片顺序及所需尺寸/文件字段 |
| 运费模板、发货及服务 | `cost_template_id`、`shipment_limit_second`及服务开关 | 根据当前店铺查询模板、类目规则和合法选项 |

接口返回与写入模型须分别核对：此次`goods_property_group`为空时必须保留`null`；误用对象及错误的草稿编号类型曾导致4000000参数解析错误，修正后正常保存。类目属性读回使用`template/mall`的已选属性；商品详情对象的`goods_property_list: null`不能独立证明属性未保存。

正常页面的已保存草稿请求中，本次实际标记为`check_status: 0`、`is_draft: false`、`is_auto_save: false`；新分配编号的初始状态为9，第一次API保存沿用该初始状态，保存后读回0。自动保存请求的`is_auto_save`为true。不能根据字段名称自行把`is_draft`改成true，也不能由这个字段独立推断已经上架。没有尝试正式发布参数。
